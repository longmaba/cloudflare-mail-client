Your Workers are deployed but no mail flows yet. This page brings the first
domain online end to end.

## 1. Create the domain administrator

Run `pnpm run setup` and use the private protected wizard that the installer
opens. Its one-use URL is saved in `.local/bootstrap.json` for resuming an
interrupted setup. Do not publish the link. Bootstrap is locked once completed.

Choose an administrator login on the configured `MAIL_DOMAIN`, such as
`admin@pilot.kieng.io.vn`, a password, and a separate external recovery inbox.
Bootstrap creates the pending organization and administrator mailbox without
sending mail. After sign-in, activate the selected domain, verify recovery
and enroll authenticator TOTP to complete onboarding.

The recovery command `pnpm --filter doota reset-admin` cannot create users.
It is only for resetting an existing superadmin; the former CLI-genesis and
external-superadmin-login instructions no longer apply.

## 2. Activate the selected domain

Follow the administrator onboarding card for the installer's configured
`MAIL_DOMAIN`. Pilot/manual mode configures the selected subdomain's DNS and
literal mailbox/alias rules to the saved inbound Worker. Existing apex MX
stays with the old provider; subdomains do not support apex catch-all rules.
The app rejects conflicting provider MX, DNS or recipient rules instead of
silently replacing them.

Native sending is configured separately for this exact domain with its
return-path, SPF, DKIM and DMARC records. Run `pnpm run doctor` and complete
the [pilot acceptance tests](https://github.com/longmaba/cloudflare-mail-client/blob/main/docs/KIENG-PILOT.md) before apex migration.
Apex routing and catch-all changes require a deliberate later cutover.

The organization is marked active only after its scoped activation succeeds.
Recovery verification can then use the working outbound path.

## 3. Create the first mailbox and user

Once the domain is `active`, provision a user through the organization:

**`/admin/organizations`** → pick the org (one org = one domain) → manage
members → create user. Because the org pins the domain, you supply only the
**local part** — Doota builds `<username>@<domain>`. Set the role (member or
admin) and an **external recovery email**.

The app creates the mailbox and scoped route, then sends a ten-minute single-use
password-setup link to the external recovery inbox. The user chooses a password
through that link; no usable password is emailed. Recovery verification is
required, and administrators must enroll authenticator TOTP.

See [Managing users](/admin/users) for the full flow.

## 4. Send and receive a test message

<Steps>
  <Step title="Receive">
    From any external account (Gmail, Outlook), email the new mailbox
    (`you@acme.com`). It should appear as a new thread within seconds. If not,
    see [Troubleshooting](/self-hosting/troubleshooting).
  </Step>
  <Step title="Send">
    Reply from Doota, or compose a new message to an external address. Watch the
    submission tick from queued → sent → delivered in the composer.
  </Step>
</Steps>

That's a working instance. From here, explore [Using Doota](/guide) or read up
on [Operations](/self-hosting/operations).
