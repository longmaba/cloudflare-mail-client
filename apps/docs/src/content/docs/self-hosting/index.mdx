Doota is meant to be run by you. This section takes a fresh Cloudflare account
to a working instance that receives and sends real mail on your own domain.

## Is self-hosting for you?

Be honest with yourself before you start — setting Doota up is a **developer-level
task**, not a point-and-click install. There's no hosted Doota to sign up for.

You'll be comfortable here if you can:

- Use a **terminal** (run commands, copy output).
- Install tools like **Node** and **pnpm**, and clone a Git repository.
- Edit a **config file** and paste in IDs.
- Manage a **domain's DNS** and a **Cloudflare account**.

Plan for **30–60 minutes** the first time.

<Aside type="note" title="Not comfortable with the above?">
  That's completely fine — this part just isn't aimed at you yet.
  - If someone has **already set Doota up** and invited you, you don't need any
    of this — go to [Getting started](/guide/getting-started) instead.
  - If you want your **own** instance, the easiest path is to have a technical
    friend or contractor follow this guide with you. It's a one-time setup.
</Aside>

Still with us? Here's what you'll need.

## What you'll need

- A **Cloudflare account with Workers Paid** for native sending ($5/month
  base, 3,000 outbound emails included monthly, then usage charges).
- A **domain** you can point at Cloudflare — Doota's model is **one deployment =
  one company = one mail domain**. You can onboard several domains, each as its
  own organization.
- **Node 24**, **[pnpm 10](https://pnpm.io)**, and a local clone of the repo.
- A **scoped Cloudflare API token** for the running app — Doota calls the CF
  API to onboard domains (zone, Email Routing, DNS, DKIM). See
  [Cloudflare API token](/self-hosting/cloudflare-api-token). (Deploying
  itself needs no token locally — you sign in through the browser.)

<Aside type="caution" title="Beta dependency">
  Outbound is sent through Cloudflare Email Sending, which is in public beta.
  It's the only supported sender — Doota is built for Cloudflare end to end.
  Factor its beta status into your risk assessment before relying on it for
  critical mail.
</Aside>

## The current deployment path

Run `pnpm run setup` from your checkout. It installs locked dependencies,
selects your Cloudflare account/zone, detects existing mail providers and
saves stable identity and secrets privately. It provisions three application
Workers and shared storage, opens protected domain-admin setup, then runs
read-only diagnostics.

Complete selected-domain activation, external recovery verification and
authenticator TOTP. Use a pilot subdomain first if the apex already receives
mail. Keep the old provider and history until staged acceptance and a deliberate
cutover. Run `pnpm run doctor` after onboarding and use `pnpm run upgrade`
for published releases. See the [current install guide](https://github.com/longmaba/cloudflare-mail-client#install).

## What each Worker binds

The guided installer deploys three application Workers. The landing/docs
rows below describe separate upstream static sites, not installed mail Workers. A queue binds to exactly **one**
consumer, so the web app only _produces_ — the async handlers live in the mail
Workers.

| Worker | D1 `DB` | R2 `MAIL_RAW` | KV `AUTH_KV` | DO `MAIL_EVENTS` | `EMAIL_SENDER` | Queues |
| --- | :-: | :-: | :-: | :-: | :-: | --- |
| **doota** (web) | ✓ | ✓ | ✓ | ✓ | ✓ | produces `inbound`, `outbound` |
| **doota-mail-inbound** | ✓ | ✓ | — | ✓ | — | produces + consumes `inbound` |
| **doota-mail-jobs** | ✓ | ✓ | — | ✓ | ✓ | consumes `outbound` + `events`, produces `outbound`; cron |
| **doota-landing** | — | — | — | — | — | — |
| **docs** | — | — | — | — | — | — |

The Durable Object class `MailEventHub` lives in `doota-mail-jobs`; the other
Workers bind to it by `script_name`. That's why `doota-mail-jobs` deploys the
DO migration.
